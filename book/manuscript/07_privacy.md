# 第7章 プライバシー：マニフェスト、申告、ポリシーのページ

審査で止まる原因の上位に、プライバシーがあります。**三つの別々のもの**を、混ぜずに整理します。

| 何 | どこにある | 何のため |
|---|---|---|
| プライバシーマニフェスト | アプリの中の `PrivacyInfo.xcprivacy` | アプリとSDKが、何を収集し、何のAPIを使うかを、機械が読める形で宣言する |
| 「Appのプライバシー」の回答 | App Store Connectの画面 | App Storeの商品ページに表示される「プライバシーの詳細」 |
| プライバシーポリシー | 公開ウェブページ（URL） | 利用者向けの説明。URLの入力が必須 |

## 7-1 プライバシーマニフェスト（PrivacyInfo.xcprivacy）

アプリに `PrivacyInfo.xcprivacy` を入れます。最低限、次のことを宣言します。

- **理由の申告が必要なAPI**を使っていれば、その種類と理由（例：`UserDefaults` を使うなら、`NSPrivacyAccessedAPICategoryUserDefaults` と理由 `CA92.1`）。
- 収集するデータの種類（収集しないなら、空でよい）。
- トラッキングの有無（`NSPrivacyTracking`）と、ドメイン（`NSPrivacyTrackingDomains`）。

### 理由の申告が必要なAPI

ファイルの更新日時、起動からの経過時間、ディスクの空き容量、`UserDefaults` など、**端末の特徴の推定に使えるAPI**が対象です。使っているのに宣言がないと、アップロードのときに、自動検証で弾かれます。自分のアプリの実行ファイルが、該当するAPIを使っているかは、`nm -u` でシンボルを調べると、おおよその見当が付きます。

### SDKのマニフェスト

AdMobやUMPなどの主要なSDKは、**自分のマニフェストを同梱**しています。アプリ側が、SDKの分を二重に書く必要はありません。ビルドに含まれているか、アーカイブの中の `Frameworks/*.framework/PrivacyInfo.xcprivacy` で確認できます。

## 7-2 実録：ITMS-91064 で、2回弾かれた

ここが、この章の山場です。

### 1回目（ビルド2）

アップロードして、数分後にこのメールが届きました。

```
ITMS-91064: Invalid tracking information - A PrivacyInfo.xcprivacy file
contains invalid tracking information at the following path:
"PrivacyInfo.xcprivacy". NSPrivacyTracking must be true if
NSPrivacyTrackingDomains isn't empty.
```

訳すと、「トラッキングのドメインが空でないなら、`NSPrivacyTracking` は `true` でなければならない」です。ところが、筆者のファイルは、**`true` で、ドメインは空の配列**でした。「空なのに、なぜ？」と首をかしげました。

調べると、Appleの開発者フォーラムに、同じ症状の報告がありました。**空の配列を置いているだけでも、この検証は不正と判定する**ことがある、というものです。その報告では、ドメインのキーそのものを削除して、通っていました。

### 2回目（ビルド3）

そこで、空の配列のキーを削除して、`NSPrivacyTracking` は `true` のまま、再度アップロードしました。**結果は、同じエラー。**

原因の読みが、半分しか合っていませんでした。Appleの説明（フォーラムで引用されているもの）には、逆向きの規則もありました。**`NSPrivacyTracking` が `true` なら、追跡ドメインを1つ以上書かなければならない。**

つまり、次の組み合わせは、すべて不正です。

| `NSPrivacyTracking` | `NSPrivacyTrackingDomains` | 結果 |
|---|---|---|
| true | 空の配列 | 不正（1回目） |
| true | キーなし | 不正（2回目） |
| false | 空の配列 | 不正になることがある（報告） |
| true | ドメインを1つ以上 | 有効 |
| false | キーなし | 有効（報告あり） |

### 3回目（ビルド4）で選んだ道

選択肢は2つでした。

- **A. `true` にして、広告のドメインを書く。** ただし、書いた追跡ドメインへの通信は、ATTで許可されなかった端末では**遮断される**。Googleの広告のドメインを書くと、許可しない人には広告が出なくなる恐れがある。しかも、正しいドメインの一覧を、Googleは公開していない。
- **B. アプリ側は `false`、ドメインのキーも書かない。** 広告SDKは、自分のマニフェストを持っている。同じ構成が審査を通ったという報告がある。広告の表示に影響しない。

筆者は、**広告が止まる危険のないB**を選びました。ATTの許可画面、同意の確認、App Store Connectの「トラッキングに使用」の申告は、そのままです。

この判断は、**Appleの公式の保証ではなく、報告に基づく**ものです。そのことを、判断の記録に残しました。アップロードして、自動検証のメールが来ないことで、はじめて確かめられます。

### 再発を防ぐ：ビルドのときに調べる

マニフェストの整合性を、リリースガード（第6章）に足しました。次の3つを、ビルドの途中で調べます。

1. ドメインのキーがあるのに、中身が空 → 失敗。
2. ドメインがあるのに、`NSPrivacyTracking` が `true` でない → 失敗。
3. `NSPrivacyTracking` が `true` なのに、ドメインがない → 失敗。

**アップロードして、メールを待つ**のは、時間がかかります。**手元のビルドで、同じ誤りを即座に検出する**ほうが、1回の試行が速くなります。

## 7-3 「Appのプライバシー」の回答

App Store Connectの「Appのプライバシー」で、**アプリと、組み込んだSDKが収集するデータ**を、種類ごとに選びます。

### まず、収集しないものを確かめる

筆者のアプリは、入力した文章や履歴を、端末の中にしか保存しません。外部には送りません。だから、**ユーザコンテンツの項目は、すべて「収集しない」**です。

### 広告SDKが収集するもの

広告（AdMob）を入れると、SDKが収集するデータの回答が必要です。Googleの公式の開示ページ（Google Mobile Ads SDKのデータ開示）には、次の種類が挙がっています。

| 種類（Appleの分類） | 内容 |
|---|---|
| 位置情報 > おおよその場所 | IPアドレスからの推定 |
| ID > デバイスID | 広告ID など |
| 使用状況データ > 製品の操作 | アプリの操作、広告の操作 |
| 使用状況データ > 広告データ | 見た広告の情報 |
| 診断 > クラッシュデータ | クラッシュのログ |
| 診断 > パフォーマンスデータ | 起動時間、ハングなど |

「ユーザに紐づくか」「トラッキングに使うか」の区分までは、Googleは示していません。**迷う場合は、保守的に（紐づく、トラッキングに使う、と）答えるほうが、後で食い違いを起こしにくい**です。ここは、最終的には、あなた自身の判断です。

### 保存したあと、「公開」を押す

**入力して保存しただけでは、反映されません。** 保存したあと、**「公開」まで進める**必要があります。筆者は、ここを見落とすところでした。

## 7-4 プライバシーポリシーのページを、公開する

**URLの入力が必須です。** しかも、`https://` から始まる**インターネットで誰でも見られるページ**でなければなりません。

### やってしまいがちな失敗

自分のパソコンの中のファイルの場所（`/Users/.../privacy-policy.html`）を入れると、次のように言われます。

> URLの形式が正しくありません。URLは次の形式である必要があります：https://example.com

**ローカルのファイルは、使えません。** 公開が必要です。

### 無料で簡単に公開する方法：GitHub Pages

1. <https://github.com/new> で、**Public**のリポジトリを作る（例 `appname-site`）。
2. `index.html`（サポートページ）と、`privacy-policy.html`（ポリシー）を置く。
3. Settings → Pages → Branch を `main`、フォルダを `/ (root)` にして保存。
4. 数分後に、`https://<ユーザー名>.github.io/<リポジトリ名>/` で見られるようになる。

**注意：ここに書いた氏名とメールアドレスは、インターネットに公開されます。** 消しても、キャッシュに残ることがあります。メールアドレスは、アプリ専用に作ったものを使うのが安全です。

アプリ自体のリポジトリではなく、**サイト専用の別のリポジトリ**を使ってください。設計書や内部の資料が、一緒に公開されてしまうのを防げます。

### ポリシーに書くこと

- 収集するデータ（しないものも明記）：入力した文章は端末内のみ、など。
- 広告のSDKが、広告ID、おおよその場所、広告の操作などを収集し得ること。
- ATTの許可の説明と、変更の方法（iPhoneの設定 > プライバシーとセキュリティ > トラッキング）。
- 課金はAppleが処理すること。
- 問い合わせ先、制定日、提供者名。

### サポートページに書くこと

**日本語のサポートURLは必須**です。よくある質問と、連絡先を書いた、簡単なページで足ります。

## ハンズオン：マニフェストと、ポリシーページを作る

| # | やること | 成功の目安 |
|---|---|---|
| 1 | `PrivacyInfo.xcprivacy` を開き、`NSPrivacyTracking` とドメインの組み合わせを、表（7-2）と照らす | 表の「有効」の行のどれかに当たる |
| 2 | アーカイブを作り、`.xcarchive` の中の `PrivacyInfo.xcprivacy` を `plutil -p` で読む | 設定した値が、そのまま出る。**空のドメイン配列がない** |
| 3 | GitHubに、サイト専用のPublicリポジトリを作る | リポジトリが作られる |
| 4 | `index.html`（サポート）と `privacy-policy.html` を置き、Pagesをオンにする | 数分後に、`https://<ユーザー名>.github.io/<リポジトリ名>/privacy-policy.html` が、ブラウザで開く |
| 5 | そのURLを、App Store Connectの「プライバシーポリシーURL」に貼る | 形式のエラーが出ない |
| 6 | 「Appのプライバシー」を回答し、保存し、**「公開」** を押す | 状態が「公開済み」になる |

**確認：** URLを、スマートフォンのブラウザで開いて、内容が読めれば成功です。

## 7-5 この章のチェックリスト

```
□ アプリに PrivacyInfo.xcprivacy を入れた
□ 理由の申告が必要なAPI（UserDefaultsなど）を宣言した
□ SDKのマニフェストがビルドに入っていることを確認した
□ NSPrivacyTracking と NSPrivacyTrackingDomains が矛盾していない
□ 空のドメイン配列を置いていない
□ ビルドのときに、マニフェストの整合性を検査している
□ 「Appのプライバシー」を回答し、「公開」まで押した
□ ポリシーとサポートを、https の公開ページにした
□ 公開ページの氏名とメールが、公開してよいものか確認した
```
