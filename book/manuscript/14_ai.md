# 第14章 AI（Claude Code）と一緒に進める作法

筆者は、アプリの実装から提出まで、AIのコーディングエージェント（Claude Code）と、ほぼ一緒に進めました。うまくいった点、危なかった点を、まとめます。

## 14-1 AIに任せてよいこと

| 作業 | 例 |
|---|---|
| 文章の下書き | 説明文、キーワード、プライバシーポリシー、サポートページ |
| 画像の生成 | UIテストで撮る、見出しを重ねる、サイズ違いを作る |
| 設定の整合性の検査 | マニフェストの規則、リリースガード、ビルド番号 |
| エラーの読み解き | ITMS-のメールを貼ると、原因の候補を挙げる |
| 直したあとの確認 | テストを書き、実行し、結果を報告する |
| 手順書、チェックリスト | この本のような資料 |

## 14-2 AIに任せてはいけないこと（あなたがやること）

1. **App Store Connect、AdMob、GitHubなどへのログインと、画面の操作。**
2. **契約の承認、口座や税務の入力、パスワードや鍵の入力。**
3. **公開の判断。** 名前やメールが公開されるページを作る、リポジトリを公開する、といった操作は、**あなたの了承を取ってから**行うよう、AIに指示しておく。
4. **AIの回答の、事実の確認。** 画面の名称、規約、金額は、変わる。

## 14-3 「実行していないことは、実行していないと言わせる」

AIは、うまくいったことを、自信ありげに報告しがちです。これを防ぐために、**報告のルールを、最初に決めます。**

- テストやビルドは、**実際に実行した結果**だけを書く。
- 実行できなかったものは、**NOT RUN（未実施）**と書く。
- 実機でしか確認できないもの（音の質、実際の広告、本番の課金）を、**シミュレータの結果で、確認済みにしない**。
- 失敗は、失敗と書く。**テストを緩めて、通さない。**

この本の第12章のような「失敗の記録」も、AIに、正直に書かせたものです。

## 14-4 別のAIに、レビューさせる

筆者は、**実装をするAIと、レビューをするAIを、分けました。** 実装したAIの自己申告ではなく、**コードと仕様とテストを独立に見て、指摘を、重大度の順に書く**役割です。レビューのメッセージには、**ビルドとテストの実行結果、未確認の点**も、書かせます。

効果があった例：

- 一時停止の直後に、文字がまとめて出てしまう、隠れた不具合を見つけた。
- テストが、実際の時間の測定に依存して、成功したり失敗したりすることを指摘した。
- 設計書の記述と、実装の食い違いを見つけた。

**指摘を直したら、回帰テスト（同じ問題が、再び起きないことを確かめるテスト）を、必ず足す**ようにしました。

## 14-5 AIの環境のつまずき

- **シミュレータが固まる。** テストが、1件も始まらずに、止まったままになることがあった。シミュレータを、一度、**停止して起動し直す**と、直った。
- **パソコンの負荷。** 他のアプリで負荷が高いと、UIテストが、数十倍遅くなる。録画が、おかしな長さになる。**負荷を確認する。**
- **長時間のコマンド。** 数分かかる処理は、**バックグラウンドで実行して、結果のログを、時々見る**ようにする。

## 14-6 役に立った依頼の仕方

- **「何を作るか」より、「何が完了の条件か」を書く。** 例：「テストが通り、画面で確認でき、仕様書が更新されている」。
- **変更の理由を、記録に残させる。** 判断の記録（ADR）に、「なぜ、そうしたか、何が未確認か」を、書かせる。
- **質問は、最小限にさせる。** AIがあなたに聞くのは、あなたしか知らないこと（名前、連絡先、価格）だけ。それ以外は、既定値を決めて進めさせる。
- **確認の頻度を決める。** 取り返しのつかない操作（公開、削除、送信）の前だけ、必ず、あなたに確認させる。

付録Dに、「実装が完了した段階で、申請に必要なものを、まとめて作らせる」依頼文を載せました。

## 14-7 この章のチェックリスト

```
□ AIに、ログイン、契約、口座、パスワードの操作をさせていない
□ 公開の前に、必ず自分の了承を取るよう、指示してある
□ 「実行した結果だけ」「未実施は未実施」と書かせている
□ 実機でしか確認できないことを、確認済みとしていない
□ 重要な判断は、記録に残している
```
